# Cutting a fork release of tmlt.analytics

How to turn a commit of this branch into the wheel that the Difference Engine
installs by URL. It describes producing `0.21.0+ep.backend.4`, and is the
counterpart of `RELEASING-ep-backend.md` in the Core fork — read that one too if
you are cutting both, because the Core wheel set has to exist first (see
[The Core build this needs](#the-core-build-this-needs)).

Nothing here publishes to PyPI, and nothing here should. The fork's version is a
PEP 440 *local version* (`0.21.0+ep.backend.4`); PyPI structurally rejects those,
which is exactly why the scheme was chosen — a fork build can never be mistaken
for, or shadowed by, an upstream release.

## What you get

Analytics is pure Python. There are no compiled extensions and nothing vendored,
so there is one wheel, tagged `py3-none-any`, valid on every platform and on
Python 3.10 through 3.12 — unlike Core, whose wheels are per-platform because it
compiles GMP, MPFR, FLINT and ARB.

That has a useful consequence: the releasable artifact can be built on a
development machine, and `uv build` is the whole of it.

```sh
rm -rf dist
uv build
```

which produces the two artifacts a release needs, on any platform:

```
dist/tmlt_analytics-0.21.0+ep.backend.4-py3-none-any.whl
dist/tmlt_analytics-0.21.0+ep.backend.4.tar.gz
```

Check the wheel before you attach it anywhere:

```sh
unzip -p dist/tmlt_analytics-*.whl '*/WHEEL'            # Tag: py3-none-any
unzip -l dist/tmlt_analytics-*.whl | grep -E '\.(so|dylib|pyd)$'   # must print nothing
unzip -p dist/tmlt_analytics-*.whl tmlt/analytics/_version.py
```

`_version.py` is generated by the Hatch version hook from `[project] version`,
so it is the one place that proves the build picked up the version you meant.

`nox -s build` runs `uv build` too, and is safe to use here (in the Core fork it
is not — there it runs cibuildwheel).

## Before you tag

1. `pyproject.toml` carries the version you are about to release, in three places
   that must agree: `[project] version`, and `[tool.uv-dynamic-versioning]`'s
   `format-jinja` and `fallback-version`. Those last two exist only so that
   `tmlt.nox_utils` can import `noxfile.py`; the note above them in
   `pyproject.toml` says why.
2. `uv lock` has been run and `uv.lock` records the new version.
3. `CHANGELOG.rst`'s Unreleased section describes what is in the build.
4. The suite is green:

   ```sh
   uv run pytest test/unit -q
   uv run pytest test/system/backend_parity -q
   uv run nox -s test-nojvm
   uv run nox -t lint
   uv run nox -s docs
   ```

   `nox -s docs` builds with `-n -W`, so an unresolved cross-reference is a
   failure; `nox -s docs-doctest` runs the examples, including the pandas-backend
   ones in the backends topic guide.

## The Core build this needs

The pandas backend binds Core artifacts that no official Core release ships:
`tmlt.core.domains.pandas_domains.PandasTableDomain` and its family, the pandas
transformations, and the pandas measurement factories. Those live on the Core
fork's **integration line** (`feature/pandas-backend`), which versions itself
`0.19.1+ep.backend.N`.

They are *not* in the published `0.19.1+ep.pandas.1` wheel set. That build is
official 0.19.1 plus `tmlt/core/utils/pandas_truncation.py` and nothing else —
`git show release/0.19.1-ep-pandas:src/tmlt/core/domains/pandas_domains.py` has
only `PandasSeriesDomain` and `PandasDataFrameDomain`. A consumer that installs
this Analytics wheel against `ep.pandas.1` will import Analytics fine and then
raise `BackendUnavailable` the moment it asks for the pandas backend.

So: **cut the Core `0.19.1+ep.backend.N` wheel set first**, following the Core
fork's runbook, and then repoint the three places in this repository that still
name the older Core build by URL. This build pairs with Core
`0.19.1+ep.backend.3`, whose integration line is what the suite here was run
against; the three URLs below still name `0.19.1+ep.pandas.1`, and stay wrong
until that wheel set is uploaded and they are repointed:

* `.github/scripts/use_core_fork_wheel.py`, `WHEEL_BASE` — the URL prefix this
  script rewrites the dev-time path source into, and therefore the Core that every
  CI job installs.
* `noxfile.py`, `_EP_CORE_WHEEL_BASE` — the URL prefix the "oldest"
  dependency-matrix cells use as a PEP 508 direct reference. Those two cells would
  otherwise install a Core that cannot run the pandas suites. (The matrix is not
  run by fork CI, which is why this has not bitten yet.)
* `pyproject.toml`, the comment above the dev-time
  `"tmlt.core" = { path = "../tumult-core", editable = true }` source, which quotes
  one of those URLs as its example.

The dev loop itself needs none of them: it resolves `tmlt.core` from a sibling
checkout of the Core fork, and a `git worktree` can be made to look like a sibling
with a symlink.

## Step 1: tag

The tag is the version with `+` and `.` turned into `-`:

| Version | Tag |
| --- | --- |
| `0.21.0+ep.backend.4` | `0.21.0-ep-backend-4` |

`nox -s make-release` is not usable here: it insists on a semantic version, on the
`main` branch, and it rewrites the changelog. Tag by hand, annotated and signed,
following the convention the Core fork's tags use:

```sh
git tag -s 0.21.0-ep-backend-4 -m "tmlt.analytics 0.21.0+ep.backend.4" -m \
"Tumult Analytics 0.21.0 (plus upstream PR #135) with the pandas backend,
work packages A1-A10. Not an official Tumult Labs release; never on PyPI."
git push origin 0.21.0-ep-backend-4
```

Pushing the tag builds nothing, and that is fine here. Every job in
`.github/workflows/release.yml` is guarded on
`github.repository == 'opendp/tumult-analytics'`, so on the fork the pipeline is
skipped in its entirety — including `Publish-To-PyPI`, which is exactly where you
want it to stay. Unlike the Core fork, this repository has no reason to enable
those jobs: the wheel is pure Python and you have already built it locally.

## Step 2: create the release and attach the wheel

```sh
gh release create 0.21.0-ep-backend-4 \
  --title "tmlt.analytics 0.21.0+ep.backend.4" \
  --notes "Fork build with the pandas backend. Not an official Tumult Labs release; never on PyPI." \
  dist/tmlt_analytics-0.21.0+ep.backend.4-py3-none-any.whl \
  dist/tmlt_analytics-0.21.0+ep.backend.4.tar.gz
```

The wheel must be a release *asset*, because the consumer below addresses it by
its `releases/download/<tag>/<file>` URL. Attaching the sdist as well costs
nothing and makes the build reproducible by anyone.

## Step 3: repoint the Difference Engine

One place outside this repository holds the URL: the **workspace-root
`pyproject.toml`** of the Difference Engine, in `[tool.uv.sources]`. Today it has
an entry for `tmlt.core` only, because Analytics still comes from PyPI. Add one
for `tmlt.analytics`, mirroring the shape of the Core entry:

```toml
[tool.uv.sources]
# tmlt.analytics is pinned to an Everyone Project build rather than PyPI because
# we need the pandas backend, which is not in any official release.
#
#   fork:     The-Everyone-Project/tumult-analytics
#   branch:   feature/pandas-backend
#   tag:      0.21.0-ep-backend-4
#   contents: 0.21.0 (plus upstream PR #135) plus the pandas backend
#
# `0.21.0+ep.backend.4` is a PEP 440 local version: it sorts after `0.21.0`,
# satisfies the `tmlt.analytics==0.21.0` requirement in
# difference-engine/pyproject.toml (a public `==` specifier ignores the local
# segment), and PyPI structurally rejects local versions.
"tmlt.analytics" = { url = "https://github.com/The-Everyone-Project/tumult-analytics/releases/download/0.21.0-ep-backend-4/tmlt_analytics-0.21.0+ep.backend.4-py3-none-any.whl" }
```

No platform markers: one `py3-none-any` wheel covers every platform, where the
Core entry needs three URLs and a marker each.

Two things about that repository must not change while doing this:

* `difference-engine/pyproject.toml` keeps its version-less `tmlt.core` entry.
  `tool.uv.sources` applies to *direct* dependencies only, so without that entry
  `tmlt.analytics` pulls the PyPI Core transitively and the source is ignored
  silently. The same reasoning is why `tmlt.analytics` itself must stay listed
  there for the new source to take effect.
* The Core URLs in the workspace root are repointed to the Core
  `0.19.1+ep.backend.3` wheel set at the same time — the build this one pairs
  with. An Analytics `+ep.backend` wheel against Core `+ep.pandas.1` is the
  combination described above that imports and then fails.

## Step 4: verify

From a clean environment:

```sh
uv sync
uv run python -c "
import pandas as pd
from tmlt.analytics import AddOneRow, KeySet, PureDPBudget, QueryBuilder, Session
from tmlt.analytics._version import __version__
from tmlt.analytics.config import config

print(__version__)
frame = pd.DataFrame({'city': ['a', 'b', 'a']})
with config.features.pandas_backend.enabled():
    session = (
        Session.Builder()
        .with_privacy_budget(PureDPBudget(1))
        .with_private_dataframe('t', frame, protected_change=AddOneRow())
        .build()
    )
answer = session.evaluate(
    QueryBuilder('t').groupby(KeySet.from_dict({'city': ['a', 'b']})).count(),
    PureDPBudget(1),
)
print(type(answer).__module__, len(answer.index))
"
```

The version must print `0.21.0+ep.backend.4`, and the answer must be a
`pandas.core.frame` dataframe with two rows. If the version prints plain
`0.21.0`, something resolved the PyPI wheel and the pin is not doing its job; if
the Session raises `BackendUnavailable`, the installed Core is not the fork's
integration build.

## Notes on the version scheme

* PEP 440 ignores the local segment when matching a specifier, so
  `0.21.0+ep.backend.4` satisfies `>=0.21.0,<0.22` and `==0.21.0` alike; and
  `tmlt.core >=0.19.1,<0.20` — this package's own requirement, unchanged from
  upstream — is satisfied by the Core fork's `0.19.1+ep.backend.3`. That is what
  makes both fork builds drop-in.
* Local segments compare alphanumerically, so `+ep.backend.1` sorts *before*
  `+ep.pandas.1`, which sorts before `0.21.1`. Nothing depends on this — every
  consumer names an exact URL — but do not rely on ordering to supersede an older
  fork build; repoint the URL.
* Bump the trailing number (`ep.backend.N`) for every release cut from this
  branch. It is a build counter, not a semantic version.

## Not determined from the repository

* Whether the Everyone Project GitHub organisation requires signed tags, and
  which key. The `-s` above follows the Core fork's runbook.
* Whether a fork release should also publish documentation anywhere. The
  `Push-Docs` job in `release.yml` is guarded to `opendp/tumult-analytics` and
  pushes to `docs.tmlt.dev`, which is not ours to write to; the docs are
  currently built locally only.
* Whether the Difference Engine wants `tmlt.analytics` pinned by URL at all, or
  would rather vendor the wheel. This runbook assumes the URL, because that is
  what the Core pin already does.
